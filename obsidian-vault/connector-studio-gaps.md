Connector Studio (see [[marketplace-connector]]) extended on 2026-07-06. Design intent + status:

- **Service-token model is the default & primary path.** Super Admin pastes one token (`auth_mode="service"`), scopes decide who sees it. Connectors are invoked as **agent tools** — the LLM extracts args from plain language and calls `execute_operation` directly; forms are NOT required for that.
- **Native exec branch**: `executor.py` now dispatches `source_type="native"` → `call_native(python_ref)` in-process (was HTTP-only). MCP branch deliberately NOT built.
- **Per-user auth**: new `connector_user_auths` table + `/api/connectors/{id}/my-connection` (GET/PUT/DELETE). `auth.py` resolves per-user creds when `auth_mode="per_user"`. Super Admin picks service vs per_user via a "Credential ownership" dropdown in the Studio Auth dialog.
- **In-chat "Connect your account" card**: `connector_agent` (agent.py) emits `[CONNECTOR_LINK_START]…[END]` marker when a user hits an unlinked per_user connector → `_postprocess` (main.py) → `interactive.type="connector_link"` → `ConnectorLinkCard.tsx` (rendered in AssistantView switch).
- **Token expiry**: on 401/403 the executor drops a `connector_reauth` nudge to the connector's `created_by` (and the failing user if per_user), deduped per connector per day.
- **OAuth2 auto-refresh (added 2026-07-06)**: `auth_type="oauth2"` config now takes token_url/client_id/client_secret/refresh_token/scope → `auth.ensure_oauth2_token` refreshes proactively (expiry buffer) + persists rotated token back to config_enc. Executor retries once on 401 for token types. Bare access_token still works (expires).
- **`connected_account` auth type (added 2026-07-06)**: MS365/Zoho "just sign in, no token typing". Reuses EXISTING `oauth_service.get_valid_token(email, provider)` + `connected_accounts` table (the "no connected_accounts table" note is OUTDATED — full auth-code+refresh flow exists for microsoft/zoho via `/api/integrations/connect/{provider}` popup). Inherently per-user; config just `{provider}`. Connect card renders "Sign in with Microsoft" (popup + postMessage `oauth-callback`) instead of field inputs (`mode:"oauth"`).
- **Form→connector /invoke wiring**: `DynamicFormWidget` submits to `/api/connectors/invoke` when `DynamicFormData.submit_target={kind:"connector",operation_id}`. INERT until some backend path actually sets `submit_target` (nothing does yet) — only needed for write-forms.

- **Questions & Access tab (added 2026-07-06)**: new ConnectorStudio tab surfacing the router-seeded questions (RouterExample rows, domain `connector:<slug>`) grouped by operation — admin can edit/add/toggle(is_active)/delete each + Regenerate (reseed). Per-operation role access: RoleMultiSelect writes operation-level ConnectorScope role rows (empty=everyone) enforced by registry.list_operations_for_user. Backend: SemanticRouterService.set_example_active/edit_example/delete_example (keep `_EXACT` cache synced) + `/api/admin/connectors/{id}/router-examples` CRUD + `/operations/{op}/roles` PUT + `/reseed`. App roles from `GET /api/access/roles`. UI uses shadcn Accordion/Switch/Badge/Popover/Checkbox/Separator.

- **Connectors as discoverable agents (added 2026-07-06)**: `capability_registry._connector_capabilities()` (60s cache) surfaces each published connector as one Capability (key `connector_<slug>`, category "Connected apps", starters = top active RouterExamples, roles from ConnectorScope role rows). Injected into `capabilities_for_role` + `nearest_capabilities` ONLY (NOT `all_capabilities()` → adoption denominator stays static). So "list all agents"/GET /api/capabilities/rescue now include connectors, role-scoped. Greeting (`_generate_greeting` in agent.py) surfaces 1 connector (statics[:3]+conns[:1]).
- **Seeder fallback (added 2026-07-06)**: when the router LLM is down, `seeder._fallback_utterances` inserts deterministic phrasings (op display_name/desc, source="kw") so a connector is never left with 0 examples → stays routable+discoverable and seeding_status becomes "seeded" not "failed" (the red AlertCircle icon in Studio = seeding_status=="failed"; fix = Regenerate/re-publish when LLM is up).

**Why:** user's mental model = admin connects portals/APIs via tokens to grow assistant knowledge; per_user is an admin-controlled option, not default. Admin wants visibility+control over the auto-generated routing phrases and who (which app role) can get answers, and connectors to behave as first-class discoverable agents.

## 2026-07-09 addendum — template gallery, analytics, write-op safety gate

Closed 3 of the gaps found in a "make it world-class" gap audit (see full audit list below):

- **Template gallery** (was the #1 "wow factor" gap): `backend/app/connectors/templates.py` — static curated catalog, each with a small hand-picked op set already shaped like `openapi_importer.parse_spec()` output. `GET /api/admin/connectors/templates` (list) + `POST /api/admin/connectors/templates/{key}/install` (create Connector+ops in one call) — registered BEFORE the `/{connector_id}` routes in connector_routes.py since a literal path must win over the int path-param route. Studio UI: "Browse Templates" button (sidebar header + empty state) → `TemplateGalleryDialog` → on install, jumps straight to `AuthDialog` pre-filled with the template's auth_type/fields/provider (`AuthDialog` now takes an optional `hint` prop).
  - **Correction (same day)**: first pass shipped 6 generic SaaS templates (Slack/GitHub/Jira/Notion/HubSpot/Zendesk) — user flagged this org doesn't use ANY of those. Replaced with apps this org actually runs: **Zoho People**, **Zoho Recruit** (both `auth_type="connected_account"`, `provider="zoho"` — ride the SAME Zoho SSO already wired for other integrations, zero secrets for the admin, but need the user's Zoho grant to include the People/Recruit scope or a reconnect is required), and **ManageEngine ServiceDesk Plus** (`auth_type="bearer"` — noted as an optional direct-API path since this org's real IT-ticket flow is email-intake into ManageEngine, not a REST call). Lesson: **default template catalogs to the org's actual SaaS stack (grep existing `services/*.py` for what's already integrated — zoho_people_service.py, zoho_recruit_service.py, manage_engine_service.py, etc.) before reaching for generic popular-app examples.**
  - Building the Zoho templates surfaced a real bug in `connectors/auth.py`: `apply_auth` hardcoded `Authorization: Bearer <token>` for both `oauth2` and `connected_account` — but Zoho's entire API surface requires `Zoho-oauthtoken <token>` instead. Fixed: connected_account now maps scheme by provider (`_CONNECTED_ACCOUNT_SCHEME = {"zoho": "Zoho-oauthtoken"}`, default Bearer), and oauth2 now reads an optional `token_scheme` key from the connector's config. Without this fix, any Zoho-backed generic connector would have silently 401'd despite a valid token.
  - Zoho **Expense**/Books was deliberately left out of the gallery — it needs a per-request `X-com-zoho-expense-organizationid` header, and the generic connector executor's `params_schema` only supports `path`/`query`/`body` locations, not `header` (see `_split_params` in executor.py). Adding header-location param support is the prerequisite before an Expense template can work.
- **Analytics**: `/{connector_id}/usage` now also returns `daily` (30-day calls/errors series), `errors` (top 5 distinct error messages), `top_users` (top 5 callers) — rendered in the Usage tab via `ChartCanvas` (reused from Analytics Studio, `type:"composed"`, first y_key=bar/rest=line). New `GET /api/admin/connectors/analytics/overview` = cross-connector leaderboard (calls, 7d calls, success rate, latency, minutes saved joined properly via ConnectorCallLog⋈ConnectorOperation, not an averaged approximation) → `AnalyticsOverviewDialog`, opened via a header button next to Help.
- **Write-op safety gate** (was a real risk — POST/DELETE tools executed immediately from the ReAct loop with zero confirmation): `ConnectorOperation.requires_confirmation` is now enforced in `connector_agent`'s tool-call loop (agent.py). A flagged op is staged via `PendingActionService` (action_type="connector_op", payload has operation_id/call_args/slug/connector_name/op_display) instead of executing, and the turn short-circuits via a local `_ConnectorConfirmationNeeded` exception with a plain "shall I go ahead? (yes/no)" message — same UX as the existing MS365/announcement write flows, not a new mechanism. New resolver strategy `_connector_pending_action_strategy` (registered on `ROUTER_RESOLVER` next to `_ms365_pending_action_strategy`) detects a yes/no against the staged `connector_op` and routes to `domain=f"connector:{slug}"` with `sub_intent="connector_op_confirm"/"connector_op_cancel"`; `connector_agent` handles those at the top of the function — confirm claims atomically (`PendingActionService.confirm`, double-submit-safe) then calls `executor.execute_operation` for real and emits a receipt via `receipt_service.emit(action_type="connector_op", ...)` so it shows up in the existing Action Receipts feed (no undo handler registered — generic external POST/DELETE has no safe generic undo).
- No DB migrations needed for any of the three — `PendingAction.payload` (JSON) and `ConnectorCallLog` already supported everything required.

Full gap audit (2026-07-09, before the above fixes) also flagged, NOT yet built: no generic OAuth2 authorization-code "Connect" button for arbitrary APIs (still manual refresh_token paste), no retry/backoff/circuit-breaker for flaky upstreams, `source_type="mcp"` is a schema stub with zero dispatch code, no incoming webhooks, no Postman-collection import, no Fernet key-rotation path.
